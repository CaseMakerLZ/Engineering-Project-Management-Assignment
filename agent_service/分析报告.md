# `agent_service` 第一版架构分析报告

> 本报告分析分支 `codex/agent-service-mvp` 中的正式 Python Agent Service。
> 该分支暂不与 `master` 合并；`master` 仍保留原有的学习型 Agent Core。

## 1. 建设目标

`agent_service` 的目标不是重新实现 Agent，而是为现有 Python Agent Core 增加一个稳定的 HTTP 服务边界，使 Java Spring Boot 后端可以通过 HTTP/JSON 创建和查询 Agent 任务。

```text
Java Spring Boot
        │ HTTP/JSON
        ▼
Python agent_service
        │
        ├── RunService：任务生命周期与业务编排
        ├── Repository：任务和消息持久化
        └── Runtime：适配现有 Agent Core
                         │
                         ├── Agent
                         ├── AgentLoop
                         ├── AgentState
                         ├── LLMClient
                         └── ToolExecutor
```

当前的关键设计是：Java 只依赖 HTTP 接口，不依赖 Python 内部类；`RunService` 只依赖 `AgentRuntime` 协议，因此未来可以把手写 `AgentLoop` 替换成 LangGraph，而不改变 Java 接口。

## 2. 目录和职责

| 文件 | 职责 |
|---|---|
| `domain.py` | 定义内部领域对象 `RunRecord`、`MessageRecord` 和任务状态 `RunStatus` |
| `schemas.py` | 定义 HTTP 请求/响应的 Pydantic 数据契约 |
| `config.py` | 从环境变量读取服务配置 |
| `api.py` | 创建 FastAPI 应用、定义 HTTP 路由和服务间认证 |
| `service.py` | 编排任务创建、后台执行、成功、失败和取消 |
| `repository.py` | 使用 SQLite 保存任务和消息 |
| `runtime.py` | 将正式服务适配到现有 Agent Core |
| `run_server.py` | PyCharm 直接运行的开发启动入口 |
| `tests/test_api.py` | 使用 FakeRuntime 的接口和生命周期测试 |

分层调用关系：

```text
HTTP Route (`api.py`)
        ↓
Application Service (`service.py`)
        ├── Repository (`repository.py`)
        └── Runtime (`runtime.py`)
                ↓
          Existing Agent Core
```

路由层不直接组装 Agent，也不直接写 SQL；Agent Core 也不知道 FastAPI 和 SQLite 的存在。

## 3. 任务生命周期

任务状态由 `RunStatus` 统一定义：

```text
CREATED
   ↓
RUNNING
   ├── COMPLETED
   ├── FAILED
   └── CANCELLED
```

### 创建阶段

Java 调用 `POST /api/internal/runs`。服务生成 UUID，创建 `RunRecord`，保存为 `CREATED`，然后把 `RunService.execute(run_id)` 放入 FastAPI 的后台任务中，接口立即返回 `202 Accepted`。

### 执行阶段

后台任务重新从 Repository 读取任务，确认它仍然是 `CREATED` 后更新为 `RUNNING`，记录 `started_at`，再调用 `AgentRuntime`。

### 成功阶段

Runtime 返回最终文本和消息列表。服务保存消息，把任务更新为 `COMPLETED`，写入 `result` 和 `finished_at`。

### 失败阶段

Runtime 或持久化流程抛出异常时，服务把任务更新为 `FAILED`，并保存错误字符串。当前版本还没有完整的异常分类体系，这是后续工作。

### 取消阶段

调用取消接口后，任务变为 `CANCELLED`。执行完成后，服务会重新读取最新状态，避免把已经取消的任务覆盖成 `COMPLETED` 或 `FAILED`。当前取消是状态层面的取消，不会强制中断已经发出的 LLM 网络请求。

## 4. API 数据传递格式

所有接口前缀为：

```text
/api/internal
```

### 4.1 健康检查

```http
GET /api/internal/health
```

响应：

```json
{
  "status": "ok",
  "service": "python-agent-service"
}
```

### 4.2 创建任务

```http
POST /api/internal/runs
Content-Type: application/json
X-Service-Token: <optional-token>
```

请求体：

```json
{
  "project_id": "project-001",
  "prompt": "请分析当前项目的代码结构"
}
```

字段约束：

| 字段 | 类型 | 说明 |
|---|---|---|
| `project_id` | `string \| null` | Java 侧项目标识，可选 |
| `prompt` | `string` | 非空，当前最多 20,000 个字符 |

响应状态码为 `202`：

```json
{
  "run_id": "d6d6c7a0-...",
  "status": "CREATED"
}
```

Java 应保存 `run_id`，而不是等待本次 Agent 执行完成。

### 4.3 查询任务

```http
GET /api/internal/runs/{run_id}
```

响应：

```json
{
  "run_id": "d6d6c7a0-...",
  "project_id": "project-001",
  "prompt": "请分析当前项目的代码结构",
  "status": "COMPLETED",
  "result": "Agent 最终回答",
  "error": null,
  "created_at": "2026-09-23T08:00:00+00:00",
  "started_at": "2026-09-23T08:00:01+00:00",
  "finished_at": "2026-09-23T08:00:12+00:00"
}
```

不存在的 `run_id` 返回 `404`。

### 4.4 查询消息

```http
GET /api/internal/runs/{run_id}/messages
```

响应：

```json
{
  "run_id": "d6d6c7a0-...",
  "messages": [
    {
      "sequence": 1,
      "message_type": "user",
      "content": "请分析当前项目的代码结构",
      "created_at": "2026-09-23T08:00:01+00:00"
    },
    {
      "sequence": 2,
      "message_type": "assistant",
      "content": {"type": "message", "role": "assistant"},
      "created_at": "2026-09-23T08:00:12+00:00"
    }
  ]
}
```

`content` 只允许 JSON 兼容内容，不能把 OpenAI SDK 对象直接暴露给 Java 或写入 SQLite。

### 4.5 取消任务

```http
POST /api/internal/runs/{run_id}/cancel
```

响应：

```json
{
  "run_id": "d6d6c7a0-...",
  "status": "CANCELLED"
}
```

## 5. 消息和持久化数据流

一次任务的消息流如下：

```text
Agent Core
   │ AgentMessage(type, content)
   ▼
CurrentAgentRuntime
   │ serialize_message()
   ▼
RunService
   │ (message_type, content)
   ▼
SQLiteRunRepository
   │ JSON.stringify(content)
   ▼
messages.content_json
```

读取时反向转换：

```text
messages.content_json
   ▼ JSON.parse
MessageRecord
   ▼ Pydantic model
HTTP JSON response
```

SQLite 当前有两张表：

### `runs`

保存一次任务的当前状态和最终结果：

```text
run_id / project_id / prompt / status
result / error
created_at / started_at / finished_at
```

### `messages`

保存任务执行过程中的消息：

```text
run_id / sequence / message_type / content_json / created_at
```

`(run_id, sequence)` 具有唯一约束，确保同一个任务中的消息顺序不会重复。

## 6. Java Spring Boot 的调用方式

Java 后端应该把 Python 服务视为一个内部 Agent Provider：

```text
用户
  ↓
Java POST /api/tasks
  ├── 创建 Java 自己的 task_id
  ├── 调用 Python POST /api/internal/runs
  ├── 保存 python_run_id
  └── 返回 Java task_id
```

之后 Java 可以：

```text
GET Python /api/internal/runs/{python_run_id}
        ↓
更新 Java Task 状态
        ↓
向前端返回任务进度和结果
```

Java 不需要导入 Python 的 `AgentState`、`AgentMessage` 或 OpenAI 类型，只依赖本报告中的 JSON 契约。

## 7. 当前第一版的问题

### 7.1 `BackgroundTasks` 不是可靠任务队列

当前后台任务仍属于 FastAPI 进程：进程崩溃、服务重启或部署迁移时，任务可能丢失。它适合单机 MVP，不适合最终的大规模任务系统。

### 7.2 SQLite 不是最终生产数据库

SQLite 适合当前学习和单机部署，但多进程写入、并发量、备份和云部署能力有限。后续应实现 PostgreSQL Repository，并保持 `RunService` 接口不变。

### 7.3 Runtime 每次任务重新组装 Agent

当前 `CurrentAgentRuntime` 每次运行都创建 `LLMClient`、`ToolRegistry`、`ToolExecutor` 和 `AgentLoop`。这样边界清楚，但长期运行时应引入应用级依赖容器和工具注册初始化，避免重复构造基础设施。

### 7.4 当前工具注册表为空

正式服务调用当前 Agent Core 时，`CurrentAgentRuntime` 创建了空的 `ToolRegistry`。因此服务已经能完成普通 LLM 任务，但还没有正式注册项目工具。下一步应建立生产工具装配入口，而不是在 API 路由中临时注册工具。

### 7.5 记忆系统尚未接入

当前保存的是 Run 和 Message，还没有 `project_memory` 表，也没有在任务开始时加载项目记忆、结束时更新记忆的流程。第一版接口已经保留 `project_id`，为后续记忆系统留下关联键。

### 7.6 错误响应还不够统一

`ErrorResponse` 已定义，但目前 FastAPI 的异常仍主要使用默认 `HTTPException` 响应。后续应增加统一异常处理器、错误码、request_id 和日志关联。

### 7.7 取消只是软取消

当前取消只能改变数据库状态，不能中断已发出的 LLM 请求或正在运行的外部工具。后续需要任务取消令牌、可取消工具和 Worker 协作。

### 7.8 缺少生产级安全与可观测性

当前只有可选的静态服务令牌。后续还需要请求日志、任务耗时、LLM 调用日志、敏感信息脱敏、重试策略、限流和并发控制。

## 8. 未来优化路线

### 第一阶段：完成 Python MVP

1. 建立正式工具装配入口并接入文件读取、代码搜索等工具。
2. 增加项目记忆表和 `MemoryRepository`。
3. 让 RunService 在运行前读取项目记忆、运行后保存分析摘要。
4. 增加更完整的 FakeRuntime 测试和 Agent 集成测试。

### 第二阶段：Java 联调

1. 在 Spring Boot 中建立 `Task`、`Project`、`Session` 模型。
2. 使用 HTTP Client 调用 `/api/internal/runs`。
3. 保存 Java `task_id` 与 Python `run_id` 的映射。
4. 实现轮询、超时和失败状态同步。

### 第三阶段：可靠任务执行

1. 将 `BackgroundTasks` 替换为独立 Worker。
2. 使用 Redis、RabbitMQ 或其他队列传递任务。
3. 增加幂等键，避免 Java 重试造成重复 Agent Run。
4. 增加并发上限、超时、重试和取消协作。

### 第四阶段：数据库和部署

1. 用 PostgreSQL 替换 SQLite。
2. 为数据库表增加迁移工具。
3. 使用 Docker Compose 部署 Java、Python、PostgreSQL。
4. 增加健康检查、日志收集和数据备份。

### 第五阶段：Agent 编排演进

1. 保留当前 `CurrentAgentRuntime` 作为手写 Loop 版本。
2. 新增 `LangGraphRuntime` 实现同一个 `AgentRuntime` 协议。
3. 对比两种运行时的 State、Tool Node、持久化和调试能力。
4. 在不改变 Java API 的前提下切换正式运行时。

## 9. 结论

当前 `agent_service` 已经完成了一个可运行的第一版服务边界：

```text
Java 可创建任务
      ↓
Python 返回 run_id
      ↓
后台执行 Agent
      ↓
保存任务状态和消息
      ↓
Java 查询结果
```

它还不是最终生产系统，但它已经完成了最重要的项目化分界：HTTP、任务、持久化和 Agent Core 不再混在一起。后续优化应优先围绕工具装配、记忆系统、Java 联调和可靠任务执行展开，而不是继续在 API 路由中堆叠 Agent 逻辑。

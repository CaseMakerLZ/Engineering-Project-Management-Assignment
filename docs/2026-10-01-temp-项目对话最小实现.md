# temp 分支：项目、对话与多轮 Turn

这份文档对应 `temp` 分支。它展示了从现有单次 Run 扩展到多轮对话的最小链路。

## 数据现在存在哪里

- Java 的 Project、Conversation、AgentTask 暂存在服务器进程内存，重启 Java 服务会清空。这里是为了先跑通业务关系，不代表最终存储方案。
- Python 的 Run 和运行消息保存在服务器本地的 SQLite。重启 Python 进程后仍在，但它不负责保存 Java 的 Project/Conversation 业务实体。
- 浏览器不保存正式业务数据。部署时，正式数据应保存在服务端数据库；后续可把 Java 的内存 Map 换成 MySQL 表和 Mapper。

## 为什么创建对话的路径带 projectId

`POST /api/projects/{projectId}/conversations` 表示“在这个项目下面新建对话”，创建时自然需要确定归属。它和 `ConversationController` 是两个概念：URL 可以嵌套，代码仍由 ConversationController 处理。创建后，对话已有自己的 ID，查询与提交 Turn 使用 `/api/conversations/{conversationId}`。若以后允许无项目对话，再新增独立创建入口即可。

## 结构与数据流

```text
Project (Java) 1 ── n Conversation (Java) 1 ── n AgentTask/Turn (Java)
                                                 │ pythonRunId
                                                 ▼
                                           Run (Python SQLite)
                                                 ▼
                                           AgentState / AgentLoop
```

一轮用户对话对应一个 Java AgentTask 和一个 Python Run。Run 内部可循环调用模型与工具多次，这些内部步骤不算新的用户轮次。

1. `POST /api/projects` 创建项目。
2. `POST /api/projects/{projectId}/conversations` 创建对话。
3. `POST /api/conversations/{conversationId}/turns` 提交用户消息，Java 创建 Python Run，返回 HTTP 202 与 task_id。
4. `GET /api/conversations/{conversationId}/turns/{taskId}` 查询当前轮次结果。
5. 同一个对话提交下一轮时，Java 查询之前的 Run 状态，将已完成轮次的用户问题与最终答案作为 context 传给 Python，最多取最近 10 轮。

也可通过 `GET /api/projects/{projectId}/conversations` 和 `GET /api/conversations/{conversationId}/turns` 查看列表。Python 原有的 `/api/internal/runs` 仍可独立使用；新字段 `conversation_id`、`context` 都是可选的。

## 当前边界

- Java 内存数据重启丢失，尚无用户认证和资源归属校验，不可作为公开网站的数据方案。
- 同一对话只允许一个未完成的 Run；第二个提交返回 HTTP 409。
- 历史上下文是“用户问题 + Agent 最终答案”，不是工具调用日志，也未做 token 数量控制或摘要。此版本只取最近 10 轮。
- Java 请求 Python 创建 Run 与本地内存记录之间没有跨服务事务；正式持久化后需要补偿、幂等与恢复策略。
- 若 Python 服务不可用，Turn 创建失败并由现有异常体系返回错误；项目与对话接口不依赖 Python。

下一阶段应先用 MySQL 持久化 Java 的三个实体并加入用户归属，再完善消息表、上下文预算与 Project Memory。

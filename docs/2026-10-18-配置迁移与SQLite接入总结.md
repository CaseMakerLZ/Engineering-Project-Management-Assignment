# 2026-10-18 配置迁移与 SQLite 接入总结

## 本日工作的背景和已确认共识

今天继续沿用此前关于本地模式、云端模式、运行数据库和 Agent 记忆系统的讨论。当前项目不是把本地和云端强行做成完全相同的实现，而是在明确边界后，让它们在 Agent Core 之前重新汇合。

已经确认的总体边界是：

```text
本地：
    TOML 管理多个本地项目
    本地 project_id 是 TOML 中的项目键
    Java 和 Python 共用同一个 SQLite 文件

云端：
    用户身份 + project_id 由服务端数据库管理
    使用 MySQL
    云端项目工作区由服务端决定

共同部分：
    得到 project_root
    创建工具注册表
    AgentRuntime / AgentLoop / Agent Core
```

本地仍然保留 `project_id`，但它不承担云端用户所有权语义。它的当前作用是：

- 从本地 TOML 中查找项目目录；
- 作为 `agent_run` 的项目归属标识；
- 为未来 Agent 日志的项目归属和检索提供稳定键。

此前讨论中还明确了记忆和日志的边界：

```text
AgentState.history
    当前运行中的热记忆，保留最近上下文

agent_log_message
    未来按需检索的冷语义记忆，记录用户、助手、工具调用和工具结果

agent_log_event
    未来的运行事件和性能日志，记录工具开始/完成、耗时、状态和错误

agent_run.context_json
    暂时保留的一次运行输入上下文快照，不是长期记忆来源
```

上下文很长并经过压缩后，Agent 需要回忆很久以前的内容时，才从独立的 Agent 日志数据库中检索有限相关片段；最近内容继续从当前运行的 `AgentState.history` 获取，不需要每次从日志数据库重新读取。

## 本日完成的代码工作

### 1. SQLiteRunRepository

已完成 `agent_service/sqlite_repository.py`，实现与 `RunRepository` 相同的最小方法集合：

```text
initialize
create_run
get_run
update_run
append_messages
list_messages
```

当前 SQLite 实现：

- 保留现有 `agent_run`、`agent_run_message` 表结构；
- 暂时保留 `agent_run.context_json`；
- 使用 WAL、外键约束、`busy_timeout` 和短事务；
- 事务失败时自动回滚；
- 在同一事务中读取最大消息序号并追加消息；
- 每个 `SQLiteRunRepository` 实例复用一条连接；
- 使用实例级锁保护这条连接；
- `close()` 用于释放当前 Python 进程中的复用连接。

这里的“一条连接”是进程内边界：PyCharm 启动一次 Python 服务通常会启动一个 Python 进程，该进程中的一个仓储实例复用一条连接。Java 进程和其他 Python 进程不能直接共享这条连接，它们各自建立连接，通过 SQLite 文件锁、WAL 和事务规则访问同一个数据库文件。

### 2. SQLite/MySQL 选择层

保留原有 `RunRepository` 接口，新增了一个很小的选择函数：

```text
create_run_repository(settings)
```

其职责只有在启动边界选择具体实现：

```text
storage.backend = "auto" + local  -> SQLiteRunRepository
storage.backend = "auto" + cloud  -> MySQLRunRepository
storage.backend = "sqlite"         -> SQLiteRunRepository
storage.backend = "mysql"           -> MySQLRunRepository
```

`RunService` 不感知数据库类型，也不需要引入大量数据库管理类。SQLite 和 MySQL 的差异留在各自的 `RunRepository` 具体实现中。

### 3. TOML 多项目配置

配置主来源已经从 `.env` 迁移到根目录 `config.toml`。本地可以配置多个项目：

```toml
[local.projects."cmc"]
name = "cmc"
root = "C:/Users/your-name/Documents/cmc"
enabled = true

[local.projects."demo"]
name = "demo"
root = "D:/javaabout/demo"
enabled = true
```

本地请求携带 `project_id = "cmc"` 后，运行时通过 TOML 查找对应的 `root`，检查项目是否启用且目录存在，再把得到的 `project_root` 交给工具注册表和 Agent Runtime。

SQLite 数据库路径也由统一 TOML 提供：

```toml
[storage]
backend = "auto"
path = "data/agent.sqlite3"
```

相对路径相对于 `config.toml` 所在目录解析，避免 Java 和 Python 因工作目录不同而访问两个不同的 `data` 目录。

`config.toml` 只保存在本机并被 `.gitignore` 忽略；`config.toml.example` 是不含真实密钥的模板。

## 下一步计划

下一阶段按以下顺序推进，避免同时修改多个尚未稳定的边界：

### 第一步：审计并固定配置契约

确认 Java 和 Python 对以下 TOML 约定完全一致：

```text
config.toml 的位置
storage.path 的相对路径基准
storage.backend 的含义
local.projects.<project_id>.root 的路径格式
runtime.mode 的 local/cloud 取值
```

### 第二步：Java/Python 共用 SQLite 的最小联调

单独处理 Java 端的 SQLite 适配，不改 Agent Core：

```text
Java SQLite JDBC DataSource
Java 端 schema 和 SQL 方言
Python SQLiteRunRepository
同一个 SQLite 文件
```

先验证 Java 创建业务任务、Python 创建和更新 `agent_run`、Java 查询任务状态的最小链路。当前表职责暂时保持分离：Java 面向用户和业务，Python 面向 Agent 执行。

### 第三步：补齐 Agent 日志的“记录”能力

等共享 SQLite 链路稳定后，再单独设计 `agent_log.sqlite3` 的两张表和写入时机。第一阶段只记录：

- 运行开始和结束；
- 工具开始和完成；
- 工具调用参数和工具结果；
- 成功、失败、耗时和错误信息。

这一阶段先保证日志可写、可查，不马上实现复杂的冷记忆检索。

### 第四步：再实现热记忆、上下文压缩和冷记忆检索的衔接

在日志数据稳定后，再确定：

```text
AgentState.history 保留哪些热内容
压缩时如何保留日志引用或摘要
Agent 何时查询 agent_log_message
查询结果如何以有限片段加入当前 history
agent_log_event 如何支持执行轨迹和性能分析
```

核心原则仍然是：最近内容由热记忆提供，较早内容按需从冷日志检索，不把整个日志数据库重新塞进模型上下文。

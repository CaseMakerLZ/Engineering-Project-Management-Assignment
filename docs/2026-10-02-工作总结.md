## 2. 本地模式与云端模式

项目最终可以支持两种部署方式：

### 本地模式

```text
Java Backend       用户本机
Python Agent       用户本机
数据库             用户本机
模型 API Key       用户自行配置
访问方式           localhost 本地端口
```

本地模式不要求登录平台账号，项目、对话、任务和运行数据都由用户本机保存。当前已经实现的 Python Agent Service 使用 SQLite；Java 端现在使用 YAML 配置的 MySQL，后续如果要实现完全轻量的本地模式，可以再增加 Java SQLite 数据源配置。

### 云端模式

```text
Java Backend       云端服务器
Python Agent       云端服务器或 Worker
数据库             云端 MySQL
模型资源           官方配置的模型供应商和凭据
访问方式           网站或公开 API
```

云端模式需要登录、用户资源归属、并发控制、任务队列和更严格的安全管理。这些能力不属于当前多轮对话最小版本，后续由用户权限模块和云端执行模块逐步补充。

需要注意：本地存储和本地执行是两个概念。只有 Java、Python 和数据库都运行在用户本机，且模型请求也由本机发起，才能称为完整的本地模式。

## 3. 四种 ID 的关系

当前业务关系为：

```text
project_id
    └── conversation_id
            └── task_id  ↔  python_run_id
```

| ID | 生成方 | 代表对象 | 当前生成方式 |
|---|---|---|---|
| `project_id` | Java | 一个项目 | `UUID.randomUUID()` |
| `conversation_id` | Java | 项目中的一段连续对话 | `UUID.randomUUID()` |
| `task_id` | Java | 用户提交的一轮任务 | `UUID.randomUUID()` |
| `run_id` | Python | Python Agent Service 实际执行的一次 Run | `uuid4()` |

Java 的 `AgentTask` 保存 `python_run_id`，因此可以通过 `task_id` 找到对应的 Python `run_id`。两者没有重复，它们分别属于 Java 业务层和 Python 执行层。

## 4. 多轮对话结构

当前采用以下层级：

```text
Project
  └── Conversation
        └── Turn / AgentTask
              └── Python Run
                    └── AgentLoop 的多个内部循环
```

一次用户提问对应一个 Java `AgentTask` 和一个 Python `Run`。一个 Python `Run` 内部可以执行多次模型调用、工具调用和状态循环，这些内部循环不算新的用户对话轮次。

第二次提交消息时，Java 会：

1. 查询该对话之前的任务；
2. 向 Python 同步仍处于 `CREATED` 或 `RUNNING` 的任务状态；
3. 收集已完成任务的用户问题和 Agent 最终回答；
4. 将这些内容作为 `context` 传给 Python；
5. Python 把上下文加入本次 `AgentState.history` 后执行 AgentLoop。

当前上下文最多传递 20 条消息，即最多 10 轮问答。这是本项目暂定的保护值，不是模型厂商或 Python 框架规定的限制。后续应改成可配置的 token 预算或上下文压缩策略。

## 5. Java 端从内存改为 MySQL

之前的临时实现使用 `ConcurrentHashMap` 保存 Project、Conversation 和 AgentTask，重启 Java 服务会丢失数据。今日已改为使用 YAML 中配置的 MySQL。

数据库表：

```text
project
conversation
agent_task
```

表之间的关系：

```text
project 1 ── n conversation 1 ── n agent_task
```

其中：

- `conversation.project_id` 外键指向 `project.id`；
- `agent_task.conversation_id` 外键指向 `conversation.id`；
- `agent_task.python_run_id` 保存 Python 运行任务的关联 ID。

## 6. MyBatis + XML 数据访问结构

按照项目约定，数据访问不使用手写 `JdbcTemplate` Repository，而采用 Mapper 接口和 XML：

```text
Service
    ↓
Mapper 接口
    ↓
Mapper XML
    ↓
MySQL
```

新增文件：

```text
JavaBackend/src/main/java/com/Agent/javabackend/Mapper/
├── ProjectMapper.java
├── ConversationMapper.java
└── AgentTaskMapper.java

JavaBackend/src/main/resources/mapper/
├── ProjectMapper.xml
├── ConversationMapper.xml
└── AgentTaskMapper.xml
```

Service 只负责业务流程：生成 ID、校验关系、组装上下文、调用 Python。Mapper 只负责数据库操作，SQL 集中在 XML 文件中。

YAML 中已补充：

```yaml
mybatis:
  mapper-locations: classpath:mapper/*.xml
```

这项配置用于让 MyBatis 加载 XML。第一次测试时遗漏了该配置，出现 `Invalid bound statement`；补充后问题解决。

表结构目前由 [schema.sql](../JavaBackend/src/main/resources/schema.sql) 提供。它只使用 `CREATE TABLE IF NOT EXISTS`，不会删除已有数据。正式项目后续应使用 Flyway 或 Liquibase 等迁移工具管理表结构版本。

## 7. 代码规范调整

针对前一版代码中“调用 `get()` 但丢弃返回值”的问题，新增了明确的存在性检查方法：

```java
projectService.requireExists(projectId);
```

含义是：

- `get(projectId)`：需要得到项目对象；
- `requireExists(projectId)`：只检查项目存在，不返回对象；
- `requireConversation(conversationId)`：需要得到对话对象；
- `requireConversationExists(conversationId)`：只检查对话存在。

同时补充了多轮上下文、Python 状态同步、实体到响应 DTO 转换和 MyBatis 数据访问边界的注释。

## 9. 当前仍存在的问题

1. Java 已使用 MySQL，但 Python Agent Service 仍使用 SQLite；两边通过 HTTP 和 `python_run_id` 关联。
2. Java 的 MySQL 表结构仍是初始版本，没有正式迁移工具。
3. 当前没有用户认证和项目资源归属校验。
4. 同一对话的并发控制仍依赖单个 Java 进程内的 `synchronized`，多实例部署时不够可靠。
5. Java 创建 Python Run 和写入 MySQL 之间没有分布式事务，可能出现孤立 Run，需要后续补偿和幂等设计。
6. Python 仍使用 FastAPI `BackgroundTasks`，进程退出时任务可能丢失。
7. 上下文暂时按消息条数限制，没有 token 预算、摘要和长期记忆。
8. Java 任务状态刷新仍需要查询 Python，后续可以考虑事件通知或更可靠的任务同步机制。
